GDD: VibePinball

Anti-Flatline guardrail. This GDD is a directory tree, not a single file. Each requirement is its own file. Coverage rows in docs/GDD_COVERAGE.json are written at requirement granularity, NOT chapter granularity. A multi-week project should produce on the order of 100+ rows, not 11. If you only have a dozen rows, your coverage is too coarse and the loop will self-terminate before the product is good.

Project pitch: A vibe coded pinball web-native game built while streaming.

How to use this directory

  • Each docs/gdd/<n>-<title>.html file is one requirement or one tightly-scoped section.
  • Each file starts with a <p data-status="..."> element: not_started | partial | done.
  • Once a file's work ships, append a <section data-role="build-log"> with what landed, the key files, and any non-obvious decisions. Build logs grow with the code.
  • Keep file names short and stable. The file path is referenced from GDD_COVERAGE.json.
  • Every section file MUST be linked from the Index below with a real <a href> hyperlink (not bare <code> text), so the index stays navigable as the tree grows.

Conventions

  • One requirement, one file, one row in the coverage ledger.
  • File names: <NN>-<kebab-title>.html, e.g. 05-vehicle-physics.html, 12-leaderboard-submit.html.
  • Cross-references between sections use relative links.
  • The em-dash ban applies here.

Index

Add entries below as sections are drafted. Each entry is a hyperlink to the section file plus a one-line description. This index is the human-readable map; the machine-readable map is docs/GDD_COVERAGE.json.

  • 01-vision-and-pillars.html: what VibePinball is and what it is not.
  • 02-table-layout.html: the Silverball Social playfield, devices, and physical table boundaries.
  • 03-physics-simulation.html: Rapier-backed ball, flipper, collision, drain, nudge, and tilt behavior.
  • 04-controls-and-input.html: keyboard, touch, and gamepad controls for play and menus.
  • 05-scoring-and-rules.html: classic-simple scoring, skill shot, bonus, lock, and multiball rules.
  • 06-camera-and-rendering.html: fixed cabinet camera, Three.js scene composition, lighting, and render readability.
  • 07-audio-and-feedback.html: mechanical audio, music bed, lamps, hit feedback, and DMD feedback.
  • 08-state-and-leaderboard.html: local settings, player identity, score submission, sanity checks, and global leaderboard.
  • 09-technical-architecture.html: Next.js, TypeScript, Three.js, Rapier, Vibekit, and module boundaries.
  • 10-testing-and-release.html: verification gates, smoke coverage, playtest criteria, and release readiness.
  • 11-physical-board-blueprint.html: real-machine board architecture, device decomposition, shot paths, and physical scale.
  • 99-out-of-scope.html: explicit v1 fences that the loop must not cross without approval.

Out of scope

A dedicated 99-out-of-scope.html file is the explicit fence. List anything that has been considered and rejected for v1, with a one-line rationale. The loop must not scope-creep into items listed there without approval.
