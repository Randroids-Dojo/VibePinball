09 Technical Architecture

Status: not_started

Spec

VibePinball uses the same web-native game pattern as nearby Vibe projects: Next.js App Router, React, TypeScript strict, Three.js rendering, Rapier 3D physics, Vibekit shared utilities, Zod validation, Vitest unit tests, Playwright smoke tests, and Vercel deployment.

Next.js app

The app uses a single primary game route with client-side runtime ownership of the render loop, input, and simulation. Server routes are limited to leaderboard and health-style needs.

TypeScript boundaries

Game logic, physics mapping, scoring rules, input action state, persistence schemas, and leaderboard validation are typed in strict TypeScript with explicit module boundaries.

Render module

The render module owns Three.js scene creation, asset setup, material setup, camera framing, resize behavior, and syncing visible meshes to simulation state.

Physics module

The physics module owns Rapier world creation, fixed-step simulation, rigid body setup, colliders, sensors, event extraction, and table device impulses.

Rules module

The rules module consumes normalized physics and input events and produces scoring, lamps, DMD messages, ball state, tilt state, bonus state, and leaderboard-ready summaries.

Vibekit usage

The project consumes Vibekit for shared math helpers, RNG when deterministic randomness is useful, storage helpers, audio context lifecycle, server KV helpers, and rate-limit primitives. Project-specific pinball rules stay local.

Asset pipeline

v1 may use authored procedural geometry and lightweight generated assets. Asset loading must fail visibly in development and degrade clearly in production.

Deployment

Vercel is the deployment target. Main branch deployment requires green verification, a healthy preview, and dedicated project storage before online leaderboard features are enabled.
